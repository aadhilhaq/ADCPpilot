Getting started

Start the server where the calculations will run, then open the address it prints in your own browser.

What it needs

These programs do the work, and the page reports any that are missing before you can submit anything:

ProgramFromNeeded for
adcp, agfr, prepare_receptor, reducethe ADCP 1.1 suite (Scripps Research)the search, the grid maps, the PDBQT file and the receptor's hydrogens. Required; install.sh installs it (see Tools).

Python 3.9 or newer with NumPy and RDKit, and, for the receptor work, PDBFixer, OpenMM and Biopython. Without those three the preparation log says which steps it had to skip. Ask the installation what it can see:

adcp-pilot check

It lists each program and the path it was found at, and names the ones it could not find. Run it before a long session: a missing program found now costs a minute, and found later costs a queued job.

On a cluster

Installation is covered in INSTALL.md in the repository. Once it is installed, start the page on the login node:

adcp-pilot serve --port 0

--port 0 lets the machine pick a free port, so two people on the same login node do not collide. It prints an address with a token:

ADCPpilot is at

    http://127.0.0.1:41823/?t=Xq4v...

The server listens on that machine only, and every request has to carry the token, so keep the address to yourself. Forward the port from your own computer and open the same address there:

ssh -N -L 41823:127.0.0.1:41823 you@login.your-cluster.edu

The desktop launcher does all of that for you: it signs in, starts the server, forwards the port and opens the browser. Closing it stops the server. For a cluster it knows by name (Grace and ACES at Texas A&M, Garibaldi at Scripps Research) only your username is typed: the address, the folders and the Slurm account and partition its jobs need are filled in.

The server submits jobs; it does not dock. Starting it on a login node is light work: it reads files, checks what you typed and hands the rest to Slurm. If your site stops long-running processes on login nodes anyway, run it inside a small interactive job and tunnel to that node instead.

A compute node usually has no route to the internet, so Fetch from RCSB fails there. Upload the structure, or browse to a copy already on the cluster.

On one machine

On a Linux workstation or laptop, or on Windows through WSL, the same interface runs the work itself, one stage after another:

adcp-pilot local

The first run installs the ADCP 1.1 suite with Scripps' own recipe, checking each Scripps package against a pinned checksum, and opens the page in your browser. Scripps builds the suite for Linux only, so on a Mac the first run installs ADFRsuite 1.0 instead and docks with ADCP 1.0, whose scores are not comparable with ADCP 1.1's (On a Mac). Runs are written to ~/adcp_runs. The header says how many cores it found, and the search settings start smaller than the cluster defaults, because settings sized for a 48 core node take hours on four.

adcp-pilot local refuses to start on a machine that has sbatch, because that is almost always a cluster login node. Use adcp-pilot serve there.

There is also a Colab notebook, which installs everything on a Google machine and shows the same interface inside the notebook. It is useful for looking around and for the example run; the cores and the session length depend on your Colab plan.

The page itself

Everything happens on one page, from the top down: the receptor, the site, the peptides, the search and the resources, then the run's name and the button, then the list of runs. Nothing is sent anywhere until you press Submit to the queue.

Five numbers across the top follow you through it: 1 Receptor, 2 Site, 3 Peptides, 4 Docking Setup and 5 Submit. Each fills green, with a tick, when the page's own checks say that step is done, and the card for the next step lights up while the ones after it stay gray. Click a number to go straight to its card. The gray is only a hint: a card can be used at any time, so a target file or an old run's settings can complete several steps at once. How each step is decided.

Every setting has a ? beside its label. It opens a panel that says what the setting does and what changes in the result if you move it, with a link to the section here that covers it at length. The panel is the same text wherever you meet it.

Two things are worth doing before your first real run: open the example run and read its table, then dock one short peptide of your own with small settings to see the whole path work. Your first run walks through both.

The build is printed at the bottom of the page. If it is not the commit you just pulled, the server is still running the old code. Stop it, start it again, then reload.

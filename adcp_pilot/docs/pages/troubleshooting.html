When something goes wrong

What the messages mean, where the logs are, and what to send if you want help.

Before anything is submitted

What you seeWhat it means
N tool(s) missingthe ADCP 1.1 suite or AmberTools is not reachable. Set ADCPSUITE_HOME and AMBERHOME, or pass --tools-root, then adcp-pilot check; or run ./install.sh again, which finds them.
ADCP 1.1 is not installed here, so nothing can dockthe interface found no ADCP 1.1 suite. ./install.sh installs it, or uses one already on the machine; adcp-pilot check says where it looked.
ADCP 1.0 (macOS) as the docking enginethis is a Mac, which docks with ADCP 1.0 because Scripps builds no ADCP 1.1 for macOS. Its scores are not comparable with ADCP 1.1 runs: compare a Mac run only with other Mac runs, or dock on a cluster or in Colab. See On a Mac.
need ADCP 1.1, which the Scripps Research Institute does not build for macOSa peptide with non-standard or D amino acids, on a Mac. Dock it on a cluster or in Colab.
this run was made on a Mac, to dock with ADCP 1.0a run started on a Mac was resumed elsewhere. Finish it on that Mac, or dock its peptides in a new run.
a fetch from the RCSB failsthe machine running the server has no route to the internet, which is normal on a compute node. Upload the file, or browse to a copy on the cluster.
no residues chosenthe site box is empty, or nothing you typed parsed as a residue.
NOT in the structurea residue you named is not there: usually the wrong chain letter, or a numbering that differs from the file's.
a peptide row marked in redthe message under it says what is wrong. Submit stays disabled until every row is valid; see what is refused.
cannot be used as a target filethe target file failed the check the run itself applies, and the reason follows: an archive that is not complete, fewer grid maps than a target holds, no receptor inside, or a file renamed after it was made. Make it again in AGFR or AGFRGUI, or clear the box and prepare the receptor here. See a target file from AGFR.
is a PDBQT receptora .pdbqt was given as the receptor. This tool prepares its receptor from a PDB or mmCIF file. To dock into a receptor you prepared yourself, make a target file from it in AGFR or AGFRGUI and give that instead.
a run with only a target file will not submitit will, once the file has been loaded: a valid target stands in for both the receptor and the site. If the target box is marked, press Load beside it and read the line under it.
A disulfide ring needs two cysteinesthis peptide is to be docked as a ring through a disulfide, by its own Ring or the run's, and has fewer than two C. Add them, or set its Ring to linear or head to tail. See a chain or a ring.
The ring is given as ..., which is not one of the choicesa peptide list's ring column holds something other than linear, head to tail or disulfide. Correct the cell, or empty it to dock the peptide as the run is set. Nothing from the list is added until then. See pasting a list.
are the same sequence, one docked as a linear chain and the other as a ringone run docks each sequence once. To compare a peptide as a chain and as a ring, dock the second in a run of its own.
sets the box and is also one of the receptor's chainsthe peptide the box is built around is ticked among the chains to keep, so it would stay in the site it marks. Untick its chain.
Keep heteroatoms is on, so ... would stay in the receptorthe ligand the box is built around is a hetero group, and keeping heteroatoms would leave it filling its own site. Turn Keep heteroatoms off.
the box from an AutoSite pocket is not drawnnot a fault: AutoSite finds the pocket on the compute node once the receptor is prepared. Load the run's target/receptor.trg in the target file box afterwards to see it. See around an AutoSite pocket.

The queue refuses it, or never starts it

What you seeWhat to do
sbatch was not foundSlurm is not in this environment. Load your cluster's environment, or use adcp-pilot local on a machine with no scheduler.
the account on the job is not one you can usefill in Account. sacctmgr show assoc user=$USER lists yours.
the walltime is longer than the partition allowslower the walltime, or name a partition that permits it under Other Slurm options.
the array is refusedyour site limits the total array size or how many tasks run at once. Max tasks at once controls concurrency, not the size of the array, so a long list may have to be split.
a task asks for more cores than a node hasset Cores per task to your node size or less.

A pending job whose reason will not clear on its own is reported in plain words on the run's row rather than being left amber; the list is in Following your runs.

The run fails part way

What you seeWhat it means
the grid target is unusablethe target file was truncated or built from another structure. It is rebuilt once automatically; twice means agfr is failing, and its output is in the prepare log.
tleap did not build topologiesthe preparation log names the residue. It is usually a heteroatom kept by Keep heteroatoms, or a gap that Rebuild missing loops would close.
the minimization was skippedsomething kept in the structure has no force field parameters, which is what keeping heteroatoms does. The results page says so.
fault(s) in the peptide bonds and residues of the rebuilt loopsa loop built by Rebuild missing loops could not be made to join the measured chain properly, with every peptide bond in and beside it trans and every residue of the L hand, so the run stopped rather than dock against it. The message names the bond or residue that failed. Untick the setting to dock the structure as measured. See rebuilding missing loops.
the prepared receptor has no hydrogensboth ways of protonating failed, and the protonation line in the preparation log says why. The run stops here because docking without hydrogens would ignore the run's pH. A structure that arrived with hydrogens of its own has them taken off first, so this is now rare.
side chains: done; left as the structure has themnot a failure: Rebuild missing side chains was off, and the line lists the residues whose missing side-chain atoms are not in the prepared receptor. See side chains.
a peptide with no MM-GBSA valuethe list of unranked peptides at the end of results.txt gives the reason for each. It has non-standard residues, which the force field has no parameters for; or it was docked as a ring and none of its top poses closes it; or the run was set up before D residues and rings were rescored, and keeps skipping them; or its rescoring failed, and the task log says why.
ring not closed in this pose: ends 4.31 Å apartnot a failure: that pose left the ring open, so it was not rescored, and the peptide's value is the mean of its closed poses. D residues and rings gives the distances a pose must meet.
a pose's line says it changed handedness, or gives the length of the closing bond after the minimizationthe minimization turned a stereocenter of the peptide into its mirror image, or did not bring a ring's closing bond to length, so that pose's energy would belong to another molecule and was not used.
the Prime engine does not score a peptide with D residues or a ringit builds its own structure, and nothing has shown it keeps these as docked. Score them with AmberTools or OpenMM.
AutoSite found no pocket to build a box aroundagfr ran its whole receptor search and returned no pocket; its own output is in target/pocket/pocket_agfr.out. Place the box around residues instead.
this is an alpha-carbon tracethe structure has one atom per residue, so every side chain is missing. Rebuilding them all is modeling rather than preparation, so the preparation stops at the start of the run.
pose N discardedthat pose's bonded terms did not cancel, so the complex was split through a molecule rather than at the interface, and its energy was not used. Look at the chain selections and the rescoring log.
the receptor was not protonated with reducereduce could not run, and PDB2PQR with PROPKA protonated the receptor instead, at the pH in the Receptor card. The reduce line of the preparation log says why; its full output is in receptor/protonated.reduce.txt.
the receptor ADapt saved has changed since this run was set upa file in the ADapt session folder was changed after the run read it back. Press Use ADapt's receptor now in the Receptor card, so ADapt writes it again.
one task of the array failedthe others are unaffected. Open the run and resume it: only the peptides with no result are docked again.
A failed preparation cannot be resumed into a result. The dock tasks wait on the prepare job and are canceled when it fails, so nothing was docked. Read the preparation log, fix what it names, and submit a new run.

Where to look

Everything is inside the run folder, which the folder button on the row will show you:

PathWhat it holds
receptor/preparation.logevery preparation step, done or skipped, with its numbers
logs/one log per Slurm job, named after its stage
docking/<peptide>/adcp.logwhat ADCP itself said, including its mode table
target/receptor_agfr.outwhat AGFR said while building the maps, with the command it was given
01_prepare.sbatch, 02_dock.sbatchthe job scripts, with the settings each stage uses written at the top
job.jsonthe settings the run was submitted with
results.txtthe table, with its cautions written underneath

The preparation log is the first place to look even when nothing failed. A run that produced a table from a receptor whose minimization was skipped, or whose site residues fell outside the box, is a run whose numbers need a footnote.

The page itself

  • A banner says the page is older than your installation. The server is still running the code it started with. Close it, start it again, then reload with Ctrl-Shift-R. The build being served is printed at the bottom of the page.
  • The address refuses you. Every request carries a token, and the address the server printed is the only one that has it. Use that address, not 127.0.0.1 on its own.
  • The page does not load through your tunnel. The port the server chose changes each time with --port 0. Forward the port it printed, or let the launcher do it.
  • The pose viewer is blank. Switch the viewer with the engine choice in the bar; Mol* is the larger of the two and takes a moment the first time.
  • A line under a view says the surface was drawn by the viewer. MSMS gave none, for the reason the line gives: the ADCP 1.1 suite's MSMS library is not installed here, the structure is larger than the server triangulates, or MSMS failed on it. The viewer's own surface is drawn instead, and nothing else is affected.
  • ADapt does not open in the Receptor card. It opens only where ADapt and ADCP 1.1 are both installed. ./update.sh says on its ADapt line where ADapt is and why, and on the next line whether ADCP 1.1 is there, with the command that adds it. While ADapt's repository is private it is not fetched, and docking works as before.
  • The Receptor card says the ADapt here is older. Embedding needs the ADapt that takes --base-path and writes _rec_H.pdb. Run ./update.sh in the ADCP_docking checkout, which brings ADapt beside the ADCP 1.1 suite up to date, and restart the interface.
  • The run did not use what was set in ADapt. The line above the frame says which receptor will be docked, and it is this page’s preparation until something is changed in ADapt, or again after Use this page’s preparation instead. Change something in ADapt, or press Use ADapt’s receptor now, and the line says the receptor as set in ADapt will be docked; ADapt writes it when you submit.

The 3D views are blank

Every 3D view on the page, and ADapt's, draws with WebGL. When the browser has it switched off, the page says so in each view: 3D view unavailable: WebGL is off in this browser. The usual reasons are a graphics driver the browser does not trust, often after a driver update, and a remote desktop session. Everything else works without it: residues are picked from the sequence, and a pose's contacts and interaction diagram are drawn as usual.

To check, open get.webgl.org, or in Chrome chrome://gpu, where the WebGL lines say whether it is available.

The way round it is software rendering, which is slower but draws everything. Quit Chrome completely, then start it with two switches:

google-chrome --use-angle=swiftshader --enable-unsafe-swiftshader

On a Mac:

open -a "Google Chrome" --args --use-angle=swiftshader --enable-unsafe-swiftshader

On Windows, run the same two switches after the path to chrome.exe, or add them to the end of the Target box of a Chrome shortcut. The switches last until Chrome is closed. Where the cause is the driver, updating or reinstalling it brings WebGL back for good.

Asking for help

Report an issue on a run's row collects that run's logs, its settings and what Slurm said, and nothing else: no poses and no structures. Send feedback in the header does the same without a run, and shows the version and machine details to paste into a message or a GitHub issue.

Whatever route you use, say what you did, what you expected and what happened instead, and include the version, the settings and the relevant log. That is almost always enough to find it.

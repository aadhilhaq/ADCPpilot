Following your runs

Every run you have made, with a coloured dot for its state, and the buttons that open it, resume it, download it or take it away. A second view walks the runs folder itself, down to every file in it.

What the dots mean

DotStateWhat is happening
pulsing greenrunninga job is working now
amberqueuedsubmitted, waiting for the scheduler
greenfinishedevery job completed
orangefaileda job failed, timed out or ran out of memory
greycancelled, or not submittedthe run exists but nothing is in the queue for it

A running dot pulses on purpose: a static green looks the same as a finished one. Open a run and each of its jobs gets its own dot and its own line, so you can see which stage is where.

The page asks the scheduler for the state every fifteen seconds while anything is live, and stops asking once everything has finished. That is deliberate: squeue on a busy login node is not free, and a page left open overnight should not keep calling it.

A job that will not start

Some pending reasons clear on their own, and some never will. A job held for one of the second kind is broken rather than queued, so the page reports it in plain words instead of showing it the same amber dot as a waiting job:

Slurm saysThe page says
PartitionTimeLimitthe walltime asked for is longer than this partition allows, so it will wait indefinitely
InvalidAccountthe account on the job is not one you can use
InvalidQOSthe QOS on the job is not one you can use
PartitionDownthat partition is down
ReqNodeNotAvailno node matching what was asked for is available
BadConstraintsthe constraints asked for cannot be satisfied

Any other reason is shown as the scheduler's own word with a note that it will not clear on its own. Fix the setting it names and submit again; reuse settings loads the run's settings back into the form so the only thing you change is the one that was wrong.

The buttons on a row

  • Open shows the run below the list: its jobs, its table once the report has run, and the pose viewer.
  • reuse settings loads this run's receptor, chains, residues, box, peptides and search settings back into the form. A failed run is a settings file, and this is the quickest way to try it again with one thing changed.
  • results downloads the tables, the report, the prepared receptor and the ranked poses. all downloads the whole run directory, grid maps included, which is much larger. The size of each is shown on the button.
  • report an issue sends the logs, the settings and what Slurm said. It does not send the poses.
  • folder shows where the run is on disk, to copy.
  • delete removes the run and everything in its folder.

Browse at the top of the card points the list at another folder, so runs made by a colleague, or by the command line somewhere else, can be opened and read here. The folder it is reading is printed beside the button.

To resize a column, drag the thin grip on the right edge of its heading; with the keyboard, tab to the grip and use the left and right arrow keys. Double click the grip to fit the column to its widest entry. The page remembers the widths in this browser, and Reset column widths, which appears under the table once a column has been resized, puts them back. The same works in the Folders view and in a run's tables.

Two views: All runs and Folders

Two tabs at the top of the card show the same runs folder in two ways. All runs is the table above, one row per run. Folders walks the folder itself: the folders in it, the folders inside those, and the files in each, with their sizes and when they last changed.

  • A folder opens when you click its name. The trail along the top, and up at the head of the list, take you back.
  • A folder that is a run, one that holds the run's settings in job.json, is labelled run and has an Open run button beside it. Inside it, Open as a run does the same. Either shows the run below, with its jobs, its table and its poses, exactly as Open does in All runs. A long run name has room: drag the grip on the right edge of the name heading to widen the column.
  • A structure, such as a pose, the prepared receptor or a complex, opens in the page's own 3D viewer when you click view.
  • A log, a table or a settings file opens as text with view.
  • The run's results files, results.tsv, results.txt and results.json, open the run's results table with open results.
  • Every file can be saved with download. A file the page cannot show, such as a target file or a packed trajectory, is a download only, and so is anything larger than 8 MB.

Only what is inside the runs folder is shown. A link inside it that leads to somewhere else is left out of the list, and the server refuses any path outside the folder, however it is written. Browse changes the folder both views read.

Resuming a run

An open run offers to resume when some of its peptides have no result. Only those peptides are docked again: the preparation, the maps and the peptides that finished are kept as they are. It is the right answer to a task that hit the walltime, to a node that died, and to a list where one peptide failed.

From the command line the same thing is adcp-dock run RUNDIR on a run that has already been submitted once.

A run whose preparation failed cannot be resumed into usefulness. Nothing was docked, because the dock tasks wait on the prepare job and are cancelled when it fails. Read logs/ and the preparation log, fix what it names, and submit a new run.

Tidying a finished run

The scratch file system counts files as well as space: on Grace each person may keep 250 000. A run holds far more files than its results need. One docked with ADCP 1.0 before trajectories were packed keeps every replica's trajectory and log loose, about 400 files per peptide, and MM-GBSA leaves some 23 working files for every pose it scores.

Tidy, under the table of an open run once a peptide has finished and none of the run's jobs is queued or running, packs the files the results no longer read into one archive in the run's archive folder, in a short job. What goes is each finished peptide's replica trajectories and ADCP's scratch, the copy of the grid maps its docking read, and the files tleap, sander and MMPBSA.py were given or left while each pose was scored. What stays is everything the results page, the pose viewer, the report, MM-GBSA rescoring, re-ranking, reuse settings and the downloads open: the tables, the ranked poses and ADCP's log, the prepared receptor and the grid maps, the energies, and each pose's topologies, minimised coordinates and decomposition, from which the interface panel is measured. A peptide that has not finished is left as it is, so a resume still docks it from what is there.

Nothing is removed until the archive has been read back and found to hold every file. Undo tidy puts every file back as it was, also in a short job; a file a later rescoring has written again is newer than the copy in the archive, and is kept. The all download carries the archive as it is. A seven peptide screen docked with ADCP 1.0 holds 3 879 files and folders; tidying packs 3 185 of them and leaves 694.

From the command line, on a compute node, python -m adcp_dock.tidy RUNDIR --dry-run lists what would be packed without touching anything, python -m adcp_dock.tidy RUNDIR tidies, and --undo puts the files back.

While you wait

The run's logs are written as it goes, and the preparation log in particular is worth reading before the docking finishes: it says what was dropped, what was rebuilt, whether the minimisation ran, and whether any of your site residues fell outside the box. If something there is not what you intended, you have learned it an hour earlier than the table would have told you.
